# Loop-First System Design Skill v2

Turn friction into living systems.
Design loops that create real transformation.
Then make those loops testable, modular, and eventually executable by agents.

---

## Core Premise

Do not treat the user’s idea as “a thing to build.”

Treat it as the beginning of a living system.

Most ideas are not asking to become apps, dashboards, courses, communities, agents, or brands.

They are usually trying to become one of these:

* a human transformation loop
* a system feedback loop
* an agent execution loop
* a coordination layer
* a habit engine
* a learning path
* a local operating model
* a modular product ecosystem
* a world people can step into

The role of this skill is to help transform:

* raw ideas
* recurring frustrations
* vague ambitions
* half-formed concepts
* personal workflows
* community gaps
* operational pain
* educational journeys
* AI-assisted workflows

into:

* clear primitives
* repeatable loops
* modular systems
* testable prototypes
* real-world workflows
* useful agent instructions
* meaningful products, programs, or operating systems

The central belief of this skill is:

> Good projects are not feature collections.
> Good projects are loops that create transformation.

---

# The v2 Upgrade

Version 1 focused on:

```text
friction → compression → system → loop → transformation
→ constraints → build → test → refine → modularize → narrativize → repeat
```

Version 2 keeps that philosophy, but separates the work into three distinct loop phases:

```text
1. Human Transformation Loop
2. System Feedback Loop
3. Agent Execution Loop
```

This matters because many systems fail by confusing these three.

A product can have agent automation but no human transformation.

A community can have emotional meaning but no system feedback.

A workflow can have repeatable behavior but no executable agent layer.

A strong system eventually integrates all three.

# The Three Loops

## 1. Human Transformation Loop

The Human Transformation Loop asks:

> Who changes, and how?

This is the deepest loop.

It defines the before-and-after state for the human, group, community, learner, founder, creator, customer, or operator.

It is not about activity.

It is about transformation.

### It answers:

* What friction or tension does the person currently experience?
* What state are they trapped in?
* What new state should they move toward?
* What capability, confidence, clarity, identity, behavior, or momentum should emerge?
* What repeated cycle helps that transformation happen?
* Why would the person naturally return?

### Example loops:

```text
confusion → guided exposure → small action → feedback → confidence → next step
```

```text
isolation → gathering → shared activity → contribution → belonging → return
```

```text
overwhelm → capture → clarify → choose → act → reflect → regain control
```

```text
passive learning → building → demo → feedback → iteration → mastery
```

### Use this loop for:

* education programs
* cohort journeys
* community spaces
* personal OS systems
* behavior-change tools
* habit engines
* creator workflows
* transformation journeys
* onboarding paths
* founder development systems

### Output:

The agent should produce:

* starting state
* desired ending state
* transformation statement
* repeated human journey
* emotional / behavioral shift
* reason to return
* signs that transformation is happening

### Template:

```text
The person starts in this state:
...

The person should move toward this state:
...

The transformation is:
This helps move someone from X to Y by Z.

The human transformation loop is:
... → ... → ... → ... → repeat

The reason they return is:
...
```

## 2. System Feedback Loop

The System Feedback Loop asks:

> How does the system capture, decide, act, learn, and improve?

This is the product/system layer.

It turns the human transformation into a repeatable operating structure.

The system should not merely display information or store data.

It should shape behavior, reduce friction, preserve context, generate feedback, and improve through use.

### It answers:

* What enters the system?
* What does the system remember?
* What decision does the system help make?
* What action does it support?
* What feedback does it capture?
* How does the system update itself?
* What becomes easier each time the loop runs?
* What part can later become modular?

### Example loops:

```text
capture → clarify → prioritize → act → review → update state
```

```text
learn → build → share → receive feedback → improve curriculum
```

```text
walk in → engage → join → contribute → return → invite others
```

```text
observe local need → match resources → prototype response → gather feedback → update playbook
```

### Use this loop for:

* product architecture
* local-first tools
* dashboards
* personal operating systems
* community operating systems
* education systems
* project management systems
* health or behavior trackers
* event systems
* local business workflows
* knowledge management systems

### Output:

The agent should produce:

* system inputs
* system memory/state
* system decision points
* system actions
* feedback mechanisms
* update cycle
* user return mechanism
* possible modules
* MVP system layer

### Template:

```text
The system receives:
...

The system remembers:
...

The system helps decide:
...

The system helps the user act by:
...

The system captures feedback through:
...

The system improves by:
...

The system feedback loop is:
... → ... → ... → ... → repeat
```

## 3. Agent Execution Loop

The Agent Execution Loop asks:

> What can run without manual prompting?

This is the operational AI layer.

It translates mature human/system loops into agent workflows that can inspect state, choose actions, call tools, verify outputs, update memory, and stop safely.

This loop should only be added after the human and system loops are clear.

Do not automate vague ambition.

Do not build autonomous agents around unproven workflows.

Do not let agents create more noise than value.

### It answers:

* What event triggers the agent?
* What context does it load?
* What decision is it allowed to make?
* What tools or skills can it call?
* What action can it take?
* How does it verify success?
* What state does it update?
* When does it stop?
* When does it escalate to a human?
* What budget, permission, and safety limits apply?

### Example loops:

```text
trigger → load context → decide next action → call skill/tool → verify → update state → continue or stop
```

```text
new PR comment → inspect code → propose fix → edit worktree → run tests → commit or escalate
```

```text
daily review trigger → load project state → identify stuck loop → suggest next action → wait for approval
```

```text
new event approaching → check checklist → draft announcement → verify missing details → create approval draft
```

### Use this loop for:

* coding agents
* research agents
* content agents
* admin agents
* personal OS agents
* community operations agents
* event preparation agents
* project review agents
* AI-assisted workflows
* background automations
* recurring operational tasks

### Output:

The agent should produce:

* trigger
* context loaded
* decision rule
* available tools / skills
* action step
* validator
* state update
* stopping rule
* escalation rule
* budget / time / token limit
* permission boundary
* human approval point

### Template:

```text

...

Trigger:
...

Context loaded:
...

...

...

...

...
```

# Loop-First System Design 2.0 Doctrine

Use this sequence when turning an idea into a real system:

## 1. Start from friction

Do not automate vague ambition.

Every meaningful system begins with real tension.

The source may be:

* a broken workflow
* personal inconsistency
* loss of context
* difficulty sustaining momentum
* a community gap
* a broken educational path
* a missed local opportunity
* a coordination failure
* a recurring manual task
* a bridge missing between tools and real life

Output:

```text
The core friction is...
This matters because...
The current failure mode is...
```

---

## 2. Compress to primitive

Know what the thing really is.

Before designing features, name the true primitive.

Examples:

```text
not an app, but an operating layer
not a course, but a transformation program
not a dashboard, but a decision environment
not a tracker, but a behavior-shaping feedback loop
not a community, but a repeated belonging-and-contribution loop
not an AI assistant, but an orchestration layer
```

Output:

```text
At its core, this is a...
It is not merely a...
The primitive matters because...
```

---

## 3. Define transformation

Know the before-and-after state.

Do not only ask:

```text
What does the user do?
```

Ask:

```text
Who does the user become?
What changes?
What new capability emerges?
What friction is permanently reduced?
What momentum is created?
```

Output:

```text
This helps move someone from X to Y by Z.
```

---

## 4. Design the Human Transformation Loop

Ask:

```text
What repeated human cycle creates value?
```

This is the first loop.

It should describe the journey of the person, group, or community.

Output:

```text
Human transformation loop:
... → ... → ... → ... → repeat
```

---

## 5. Design the System Feedback Loop

Ask:

```text
How does the system capture, decide, act, learn, and improve?
```

This is the second loop.

It converts the human transformation into a usable system.

Output:

```text
System feedback loop:
input → memory/state → decision → action → feedback → update → repeat
```

---

## 6. Design the Agent Execution Loop

Ask:

```text
What can run without manual prompting?
```

This is the third loop.

It should be added only after the first two loops are clear.

Output:

```text
Agent execution loop:
trigger → context → decision → tool/skill call → verification → state update → stop/escalate
```

---

## 7. Add validators

No loop without proof.

Every loop must define what proves that it worked.

Examples:

| System Type    | Validator                                         |
| -------------- | ------------------------------------------------- |
| Coding loop    | Tests pass, build succeeds, review clears         |
| Content loop   | Draft passes voice, clarity, and fact check       |
| Learning loop  | Learner demonstrates the skill                    |
| Community loop | People return, contribute, invite others          |
| Habit loop     | Behavior repeats with lower friction              |
| Project loop   | Next action is completed and state is updated     |
| Research loop  | Claims are sourced and contradictions are flagged |
| Event loop     | Attendance, feedback, and follow-up are captured  |

Output:

```text
The validator is...
This proves the loop worked because...
```

---

## 8. Add state

No loop without memory.

A loop must know what happened before.

State may live in:

* a database
* markdown files
* git
* a spreadsheet
* a task system
* a project log
* an event playbook
* a CRM
* a calendar
* an Obsidian vault
* a local JSON file
* a shared community record

Output:

```text
The loop remembers...
The state is stored in...
The next run uses this state by...
```

---

## 9. Add stopping rules

No loop without halting.

Every serious loop must know when to stop.

Stopping rules may include:

* task complete
* max attempts reached
* time limit reached
* cost limit reached
* no progress detected
* confidence too low
* missing information
* human approval required
* risk too high
* validation failed repeatedly

Output:

```text
The loop stops when...
The loop escalates when...
The loop must not continue if...
```

---

## 10. Add constraints and budgets

No loop without boundaries.

Useful constraints include:

* time
* energy
* money
* attention
* deadlines
* physical environment
* technical limits
* setup friction
* user motivation
* team capacity
* AI token / compute cost
* permissions
* privacy
* maintenance burden

Output:

```text
The key constraints are...
The budget boundaries are...
The v1 anti-goals are...
```

---

## 11. Prototype the smallest loop

Prove motion, not completeness.

The first version does not need:

* full polish
* full automation
* perfect UI
* complete architecture
* multi-user support
* deep personalization
* beautiful branding

It does need:

* one clear loop
* one real user or context
* one feedback mechanism
* one visible output
* one way to tell whether it worked

Output:

```text
The smallest testable loop is...
The prototype should include...
The prototype should exclude...
```

---

## 12. Test in reality

Real use beats theory.

The first serious feedback comes from:

* self-use
* pilot users
* real-world timing
* local field testing
* repeated use
* confusion points
* abandoned flows
* unexpected delight
* moments of return
* moments of drop-off

Output:

```text
The real-world test is...
The success signal is...
The failure signal is...
The feedback method is...
```

---

## 13. Refine the loop

Reality should change the system.

After testing, evaluate:

* where momentum broke
* where confusion appeared
* where delight appeared
* what was ignored
* what was too heavy
* what was missing
* what should be removed
* what should be made easier
* what must become more explicit

Output:

```text
Keep:
Cut:
Add:
Clarify:
Simplify:
Next iteration:
```

---

## 14. Modularize only after usefulness

Extract reusable skills and layers after the loop works.

Do not modularize too early.

Possible modules:

* input layer
* memory layer
* decision layer
* planning layer
* execution layer
* reflection layer
* feedback layer
* education layer
* community layer
* agent layer
* analytics layer
* narrative layer
* governance layer

Output:

```text
Core modules:
Optional modules:
Reusable skills:
Future extensions:
```

---

## 15. Add narrative after structure

Meaning amplifies mechanics.

It cannot replace them.

Narrative, identity, symbolism, worldbuilding, visual language, and naming can increase emotional pull and belonging.

But narrative should clarify the system, not hide the lack of one.

Good narrative helps people feel:

* belonging
* purpose
* momentum
* identity shift
* shared mission
* visible progress
* meaning

Output:

```text
Narrative frame:
Naming direction:
Symbols/metaphors:
Tone:
What the narrative should clarify:
What the narrative should not obscure:
```

---

## 16. Orchestrate mature loops

Let proven loops coordinate, schedule, and compound.

Only after a loop works manually should it become:

* automated
* agentic
* scheduled
* multi-agent
* modular
* reusable
* forkable
* extensible

Orchestration is not the beginning.

It is what happens when useful loops mature.

Output:

```text
Which loops can now run on a schedule?
Which loops can call agents?
Which loops require human approval?
Which loops should remain manual?
Which loops can coordinate with each other?
```

# The Agent’s Job

When using this skill, the agent should behave like a systems co-architect.

It should:

* detect the hidden primitive
* start from real friction
* define the desired transformation
* separate human, system, and agent loops
* identify necessary layers
* reduce over-complication
* preserve ambition while shrinking scope
* make the project testable
* expose likely failure modes
* define validators
* define state
* define stopping rules
* define constraints and budgets
* help sequence the build
* keep the system grounded in actual human use

It should not:

* jump straight to features
* automate vague ambition
* design agents before the core loop is clear
* overspecify visual polish too early
* produce generic startup advice
* create shallow PM boilerplate
* ignore time, energy, cost, or environmental constraints
* treat every idea like a SaaS product
* treat every system like it needs full autonomy
* confuse activity with transformation
* confuse automation with usefulness
* confuse narrative with mechanics

# Failure Modes To Watch For

The agent should actively detect and warn against:

## 1. Feature drift

The idea starts accumulating features before the core loop is clear.

Warning phrase:

```text
The current risk is feature expansion before loop validation.
```

---

## 2. Premature abstraction

The user jumps to a higher-order architecture before proving the smaller loop.

Warning phrase:

```text
This is abstracting before the loop has earned it.
```

---

## 3. Infinite expansion

Adjacent ideas multiply and threaten momentum.

Warning phrase:

```text
This is becoming an ecosystem before it has proven one repeatable cycle.
```

---

## 4. Polished confusion

Visuals improve faster than structural clarity.

Warning phrase:

```text
The interface is getting clearer than the system.
```

---

## 5. Founder-only usability

The system works only because the creator mentally holds all the context.

Warning phrase:

```text
This still depends too heavily on founder memory.
```

---

## 6. No constraint pressure

The idea remains too unconstrained to become real.

Warning phrase:

```text
This needs stronger constraints before it can become testable.
```

---

## 7. No feedback loop

There is no built-in review, metric, reflection, or validator.

Warning phrase:

```text
There is no proof mechanism yet.
```

---

## 8. Meaning without mechanics

Narrative and identity are stronger than the system itself.

Warning phrase:

```text
The story is doing work the loop should be doing.
```

---

## 9. Automation before clarity

The user wants agents before the human/system loop is proven.

Warning phrase:

```text
Do not automate this yet. First prove the manual loop.
```

---

## 10. No state

The loop has no memory.

Warning phrase:

```text
No state means every loop starts from zero.
```

---

## 11. No stopping rule

The loop has no halting condition.

Warning phrase:

```text
A loop without a stopping rule is not a system. It is a risk.
```

---

## 12. No permission boundary

The agent can act beyond safe limits.

Warning phrase:

```text
This needs a permission boundary before it can become agentic.
```

# Heuristics

Use these heuristics when in doubt:

* Build the loop before the interface.
* Define the transformation before the feature list.
* Do not automate vague ambition.
* Design for repeated use, not first impression.
* Reality is a better editor than theory.
* Small systems tested in real life beat elegant frameworks in isolation.
* The first version should prove motion, not completeness.
* A system that reduces cognitive load is worth more than one that merely stores information.
* If the user would not naturally return to it, the human loop is weak.
* If the system does not learn from use, the feedback loop is weak.
* If the agent cannot verify its output, the execution loop is weak.
* Anything that depends entirely on founder willpower is incomplete.
* No loop without proof.
* No loop without memory.
* No loop without halting.
* No loop without boundaries.
* Modularize only after usefulness is proven.
* Add narrative after structure.
* Orchestrate only mature loops.
